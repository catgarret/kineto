# Module taxonomy — 모듈은 어느 카테고리에 속하는가

모듈마다 카테고리는 **정확히 하나**입니다. 이 문서는 그 하나를 고르는 규칙이고,
`scripts/generate-module-metadata.mjs`의 `CATEGORIES` 맵이 실제 원본입니다.
데모의 섹션, 사이드바 그룹, Module Index, 사용 매트릭스는 전부 그 맵에서
생성됩니다. 손으로 적는 목록은 없습니다.

## 왜 규칙이 필요한가

v0.11.0 이전에는 카테고리가 세 곳(데모 DOM 섹션, 사이드바 `MODULE_GROUPS`,
문서)에 따로 적혀 있었습니다. 그래서:

- `dither` · `ascii` · `halftone`은 "이미지에 질감을 입히는 효과"인데 Lazy(지연
  로딩)의 variant로 들어가 Media 섹션의 로딩 카드들 사이에 놓였습니다.
- `marquee`는 사이드바에서 Media인데 실제 카드는 Text 섹션에 있었습니다.
- `coverReveal`은 사이드바에서 Media인데 카드는 Scroll 섹션에 있었습니다.
- `ripple`은 사이드바에서 Pointer인데 카드는 Feedback 섹션에 있었습니다.

전부 같은 원인입니다. 원본이 하나가 아니면 반드시 어긋납니다.

## 결정 순서

위에서부터 읽고, **처음 맞는 규칙에서 멈춥니다.** 순서 자체가 애매함을
없애는 장치이므로 "더 잘 어울리는 것 같다"로 아래 규칙을 앞지르지 않습니다.

| 순서 | 카테고리 | 규칙 |
|---|---|---|
| 1 | `system` | 콘텐츠를 덮거나 문서 사이의 전환을 다루는, 페이지 전체 수준의 모듈 |
| 2 | `media` | 이미지·영상을 **가져오고(로딩) 보여주고 탐색**하는 모듈. 픽셀을 다시 그리지는 않음 |
| 3 | `effects` | 이미 렌더된 대상의 **픽셀을 캔버스로 다시 그리는** 그래픽 효과 모듈 |
| 4 | `components` | 키보드와 ARIA 상태를 가진 UI 위젯 |
| 5 | `text` | **글자 자체**를 다루는 모듈 |
| 6 | `scroll` | 스크롤 위치나 속도가 **구동**하는 모듈 |
| 7 | `pointer` | 포인터·기기 입력이 **구동**하는 모듈 |
| 8 | `feedback` | 사용자 행동의 **결과와 상태를 알리는** 모듈 |

## 경계선에 있는 모듈들

규칙만으로는 헷갈릴 수 있는 것들의 판정 근거입니다. 새 모듈이 이 중 하나와
닮았다면 같은 논리를 그대로 적용하세요.

**`lazy`(media) vs `stylize`(effects)** — 이 분류 체계가 생긴 계기입니다.
Lazy가 하는 일은 이미지를 *가져오는* 것이고, 전환 효과는 도착할 때까지의
빈자리를 메우는 수단입니다. Stylize가 하는 일은 이미 있는 픽셀을 *다시 그리는*
것이고, 로딩과는 아무 상관이 없습니다(`mode: persist`는 미디어가 살아 있는 내내
유지됩니다). 그래서 `dither` · `ascii` · `halftone`은 Lazy의 variant일 수
없습니다. **"가져오는 일이면 media, 다시 그리는 일이면 effects."**

**`glitch`(effects)** — 텍스트 variant(`rgb` · `pixel` · `noise`)도 있지만
`image` · `reveal` · `datamosh` · `crt` · `vcr`가 캔버스로 픽셀을 다시 그립니다.
규칙 3이 규칙 5보다 앞서므로 effects입니다. 모듈을 텍스트용·이미지용으로
쪼개면 같은 알고리즘이 두 벌이 되므로 쪼개지 않습니다. 대신 데모가 한 섹션
안에서 대상별로 나눠 보여 주고, 그 구분의 원본은 계약의 `variantRequires`입니다.

**`cardGlow` · `tilt`(pointer)** — 겉모습을 바꾸지만 캔버스로 픽셀을 다시
그리지 않고, 포인터 입력이 없으면 아무 일도 일어나지 않습니다. 규칙 3에
걸리지 않으므로 규칙 7입니다.

**`brushReveal` · `ambientMedia`(effects)** — 포인터나 재생에 반응하지만 하는
일은 캔버스 마스크와 캔버스 샘플링, 즉 픽셀을 다시 그리는 것입니다. 규칙 3이
규칙 7보다 앞섭니다.

**`ripple`(feedback)** — 포인터가 구동하지만 목적은 "눌렸다"는 결과를 알리는
것입니다. 규칙 8이 목적을 말하고, 규칙 7은 수단을 말합니다. 목적이 이깁니다.

**`fullpage`(scroll)** — 화면 전체를 차지하지만 콘텐츠를 덮지도, 문서를
전환하지도 않습니다. 구동하는 것은 스크롤입니다.

**`lightbox` · `slider` · `radial`(media)** — 키보드와 ARIA를 갖춘 위젯이지만
다루는 대상이 이미지·영상입니다. 규칙 2가 규칙 4보다 앞섭니다.

**`textFill`(text)** — 스크롤이 진행률을 주지만 대상은 글자입니다. 규칙 5가
규칙 6보다 앞섭니다.

## 새 모듈을 추가할 때

1. 위 표를 위에서부터 읽고 카테고리를 하나 고릅니다.
2. `scripts/generate-module-metadata.mjs`의 `CATEGORIES`에 추가합니다.
   빠뜨리면 생성이 실패합니다.
3. 데모 카드를 그 카테고리의 섹션(`[data-demo-category]`) 안에 놓고,
   대표 카드 하나에 `data-demo-home="<모듈명>"`을 답니다.
4. `npm run test:taxonomy`가 위 세 가지의 일치를 검사합니다.

데모 카드가 많아도 블록이 끝없이 길어지지 않습니다. 모듈 블록은 **처음 두 줄**의 카드만
보여 주고 나머지는 "데모 더 보기" 버튼 뒤에 둡니다(`demo/fold.js`). 대표 카드와 가장 먼저
보여 줄 카드를 마크업 앞쪽에 두세요. 모든 variant를 한 번에 보는 곳은 블록 위의
"모든 variant 비교" 시트입니다([variant 비교](variant-compare.md)). 접힌 카드는 잘려서 가려질 뿐
크기를 유지하고(`display:none`이 아니므로 모듈 측정이 깨지지 않음) `inert`로 키보드에서
빠집니다. 카드로 스크롤하는 코드는 먼저 `KINETO_FOLD.reveal(el)`을 부르거나 그 요소에
`kt-demo:reveal` 이벤트를 보냅니다.

## 무엇이 검사되는가

`tests/module-taxonomy.mjs`가 CI에서 다음을 강제합니다.

- 공개 모듈은 전부 카테고리를 하나 선언해야 하고, 그 값은 알려진 카테고리여야 합니다.
- 데모에는 카테고리마다 정확히 한 개의 `[data-demo-category]` 섹션이 있어야 합니다.
- 모듈마다 `data-demo-home` 표식이 정확히 하나여야 합니다. 두 개면 어느 쪽이
  대표인지 알 수 없고, 없으면 사이드바가 갈 곳을 잃습니다.
- 그 표식은 **선언한 카테고리의 섹션 안에** 있어야 합니다. 이 한 줄이
  "사이드바는 Media인데 카드는 Text 섹션" 같은 어긋남을 불가능하게 만듭니다.
- 데모는 그룹 목록을 손으로 적지 않아야 합니다(생성된 분류를 읽어야 합니다).
