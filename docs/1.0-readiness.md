# 1.0 계약 준비도

1.0은 모듈 수가 아니라 공개 계약을 예측할 수 있는지로 판단합니다. 이 문서는 현재 자동 검증과 남은 외부 조건을 분리해 기록합니다.

| 영역 | 현재 상태 | 근거 또는 남은 조건 |
|---|---|---|
| Core API·module registry | 완료 | feature contract와 52개 registry parity 검사 |
| option naming·기본값 | 완료 | contract·playground·defaults·variant-options 검사 |
| instance return shape·destroy | 완료 | update/lifecycle/leak·framework QA |
| entry·타입 호환성 | 완료 | full/modular/adapter package·TypeScript 검사 |
| 브라우저 지원표 | 진행 | Chromium 전체와 heavy-layout Firefox/WebKit은 고정; 일반 모듈 smoke 범위는 계속 기록 |
| 오류 코드·debug mode | 완료 | `Kineto.diagnosticCodes`, `Kineto.diagnostics`, opt-in sink·subscription·최근 50개 history와 validation을 Node 테스트로 고정 |
| deprecation 정책 | 진행 | patch/minor/major 원칙은 [계약 문서](diagnostics-and-deprecation.md)에 고정; 실제 deprecated API가 생길 때 migration fixture 필요 |
| 모듈 유지 상태 | 기준선 | [유지 상태표](module-status.md)는 52개를 contract-stable로 기록; maintenance/experimental 승격 조건은 별도 검토 |
| 외부 실제 사용 사례 | 조건 | 최소 3개 case study 또는 독립 소비자 피드백 필요 |

## 동결 전 원칙

- 새 public API는 두 개 이상의 실제 사용 사례와 Vanilla Core 계약을 먼저 확보합니다.
- 어댑터가 Core와 다른 의미를 만들면 어댑터가 아니라 Core 계약을 수정합니다.
- 모든 계약 변경은 영문 changelog 뒤에 한국어 대응 항목을 추가하고, package·types·demo·docs를 함께 갱신합니다.
- 1.0 전에는 모듈 수를 늘리는 것보다 entry 비용, lifecycle, 접근성, browser evidence를 우선합니다.
